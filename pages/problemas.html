Problemas: a mesma técnica, movimentos diferentes

Ponto de atenção permanente: o problema que cair na prova pode ser qualquer um — não presuma que repete o de outra turma ou o dos exemplos deste site. PRCP, TSP e PET aparecem aqui como treino. O que se repete é o modo de pensar (as 4 peças e as 5 perguntas). Se você sabe derivar o movimento, a vizinhança, o sinal e o desfazer de um problema novo, está preparado. Treine isso na seção Problema inédito.

Cada problema é preenchimento das 4 peças. Para cada um: a solução, o movimento, como enumerar a vizinhança, o sinal, como desfazer e a armadilha. PRCP, PET e TSP têm código executável em codigo/; PAB, DARP e hubs trazem o raciocínio (a descrição vem dos enunciados em exercicios/).

PETEscalonamento de Tripulações — a sua P2 minimiza

Tarefas (trechos de viagem com início/fim) são distribuídas entre tripulações (motorista + cobrador). A FO soma ociosidade, hora extra, sobreposição e excesso de jornada (as duas últimas com peso 100).

Soluçãomatriz_sol[tripulação][k] (tarefas, ordenadas por início) + quantidade[tripulação]
Movimentotirar 1 tarefa de uma tripulação e inseri-la em outra
Enumerar3 laços: origem × posição na origem × destino (≠ origem)
Desfazerrestaurar as duas linhas mexidas (origem e destino) e a fo
Armadilhaminimização → <. Inserção ordenada por início: se inserir no fim, a ociosidade/sobreposição sai errada.

Primeira melhora do PET (verificada). Repare nos 3 laços e no desfazer das duas linhas:

void busca_local_primeira_melhora(Solucao& s)
{
    LinhaSalva salva_origem, salva_destino;
    int melhorou = 1;
    calcular_fo(s);
    while (melhorou == 1)
    {
        melhorou = 0;
        for (int origem = 0; origem < num_tripulacoes && melhorou == 0; origem++)
        {
            for (int posicao = 0; posicao < s.quantidade[origem] && melhorou == 0; posicao++)
            {
                int tarefa = s.matriz_sol[origem][posicao];
                for (int destino = 0; destino < num_tripulacoes && melhorou == 0; destino++)
                {
                    if (destino == origem)
                        continue;
                    int fo_original = s.fo;
                    salvar_linha(s, origem, salva_origem);
                    salvar_linha(s, destino, salva_destino);
                    remover_tarefa(s, origem, posicao);   // aplica o movimento
                    inserir_tarefa(s, destino, tarefa);
                    calcular_fo(s);
                    if (s.fo < fo_original)
                        melhorou = 1;                     // fica aplicado
                    else
                    {
                        restaurar_linha(s, origem, salva_origem);   // desfaz
                        restaurar_linha(s, destino, salva_destino);
                        s.fo = fo_original;
                    }
                }
            }
        }
    }
}

void busca_local_melhor_melhora(Solucao& s)
{
    calcular_fo(s);
    while (1)
    {
        int melhor_i = -1;
        int melhor_j = -1;
        double melhor_fo = s.fo;
        for (int i = 0; i < num_cidades - 1; i++)
        {
            for (int j = i + 1; j < num_cidades; j++)
            {
                double fo_original = s.fo;
                trocar(s, i, j);
                calcular_fo(s);
                if (s.fo < melhor_fo)
                {
                    melhor_fo = s.fo;
                    melhor_i = i;
                    melhor_j = j;
                }
                trocar(s, i, j);                      // sempre desfaz
                s.fo = fo_original;
            }
        }
        if (melhor_i == -1)
            break;
        trocar(s, melhor_i, melhor_j);
        s.fo = melhor_fo;
    }
}

PABAlocação de Berços minimiza

Cada navio vai para um berço e tem um horário de atracação. FO = soma dos tempos de serviço (espera + atendimento) de todos os navios; as restrições (janela do navio, abertura/fechamento do berço, t = 0 = berço incompatível) entram como penalização.

Solução (típica)para cada berço, a sequência de navios; os horários de atracação saem da FO (cada navio atraca quando chega e o berço está livre)
Movimentos candidatos(a) mover 1 navio para outro berço; (b) trocar a ordem de 2 navios no mesmo berço
Enumerarnavio × berço destino (× posição de inserção)
Desfazerrestaurar as linhas dos berços mexidos
Armadilhamover um navio para berço em que t = 0 → inviável (penalizar forte); horários dependem da ordem: recalcule todos a partir da sequência.
Ponto de decisão: o enunciado deixa a representação livre ("tratadas na modelagem e/ou penalização"). Na prova o .h trará a struct; aceite a dela e derive o movimento do gerar_vizinha fornecido.
DARPDial-a-Ride (transporte de PPNEs) minimiza

Vans atendem requisições (embarque + desembarque, com janelas de tempo e capacidade). FO = ponderação de nº de veículos, distância, duração das rotas, tempo de viagem e espera. As restrições (janela, capacidade, tempo máximo) viram penalização.

Solução (típica)para cada veículo, a sequência de locais visitados (embarque da requisição r antes do desembarque dela)
Movimentoremover uma requisição inteira (os dois locais) de um veículo e reinseri-la em outro
Enumerarrequisição × veículo destino (× posições de inserção)
Desfazerrestaurar as rotas dos dois veículos
Armadilhamover só um dos dois locais da requisição quebra a precedência (embarque antes do desembarque) e a "1 requisição = 1 veículo". Mova o par.
HUBSUMApHCP — p-hub centro minimiza
Soluçãovet_sol[n]: as p primeiras posições são os hubs; as outras, os não-hubs
Movimentotrocar um hub (posição < p) por um não-hub (posição ≥ p)
Enumerarfor h < p × for v ≥ p → p(n−p)
Desfazerrepetir a troca
Armadilhaa FO é o máximo entre todos os pares (e custa O(n²) ou mais por avaliação): a busca é cara — evite avaliações desnecessárias. Minimização → <.

Observação: aqui o movimento é uma troca entre dois blocos do vetor, não entre quaisquer duas posições (trocar dois hubs entre si não muda a solução).

A. Coloração de vértices — grafo com n vértices e k cores; minimizar o número de arestas cujas pontas têm a mesma cor.
  • Solução: vet_cor[vertice] (0..k−1).
  • Movimento: mudar a cor de um vértice → n(k−1) vizinhos.
  • Sinal: minimiza (<). Desfaz: restaurar a cor.
  • Ponto de atenção: ao mover um vértice, só as arestas incidentes a ele mudam — dá para calcular a variação sem refazer a FO inteira (bônus de eficiência).
B. Partição em 2 grupos — dividir n números em dois grupos minimizando |soma do grupo 0 − soma do grupo 1|.
  • Solução: vet_grupo[i] ∈ {0, 1}.
  • Movimento: trocar o grupo de um número → só n vizinhos (com 2 grupos, "outro valor" é 1 − atual; não precisa do sorteio com do/while).
  • Sinal: minimiza. Desfaz: inverter de novo (o movimento é o seu próprio inverso).
  • Ponto de atenção: o valor absoluto na FO — esquecer o abs faz a busca "melhorar" produzindo diferença negativa enorme.
C. Selecionar exatamente k itens — escolher exatamente k de n itens para maximizar a soma dos valores.
  • Solução: vet_escolhido[i] ∈ {0, 1}, com exatamente k uns.
  • Movimento: virar um único bit quebraria a restrição (ficaria com k±1). O movimento correto é trocar: tirar um item escolhido e pôr um não escolhido → k(n−k) vizinhos.
  • Sinal: maximiza (>). Desfaz: repetir a troca.
  • Ponto de atenção: a restrição do problema pode mudar o movimento. Quando o movimento "óbvio" gera solução inviável, procure um movimento que preserve a viabilidade (ou penalize na FO).

EXERCÍCIO CSelecionar exatamente k itens — resolvido do zero maximiza
Ponto de atenção permanente: este problema é treino. O da prova pode ser outro. O que vale levar é o caminho: enunciado → solução → movimento → vizinhança → sinal → desfazer → código → teste.

Parte 1 — Entender o enunciado

Enunciado: escolher exatamente k de n itens para maximizar a soma dos valores.

Antes de qualquer código, separe o enunciado em quatro caixas:

CaixaNeste problemaPor que importa
Dadosn, k, vet_valor[i]viram variáveis globais
Decisãocada item entra ou nãodefine a struct de solução
Restriçãoexatamente k escolhidosmuda o movimento (Passo 3)
Objetivomaximizar a somadefine o sinal >
Onde o enunciado pode ser diferente: "exatamente k" não é "até k" nem "pelo menos k" — com "até k", virar um único bit passa a ser válido. Releia essa palavra. Se os itens tivessem pesos e uma capacidade, seria uma mochila (a restrição vira soma, não contagem). Se o objetivo fosse minimizar, o sinal inverte.

Parte 2 — Plano do que fazer

  1. Definir a solução (o que o vetor guarda).
  2. Escrever calcular_fo.
  3. Decidir o movimento, respeitando a restrição.
  4. Contar a vizinhança (custo e forma dos laços).
  5. Escrever gerar_vizinha e uma construtiva aleatória.
  6. Escrever as 3 buscas.
  7. Testar por um segundo caminho.
  8. Compilar de novo no final.

Em prova real, 1, 2 e 5 costumam vir prontos. Treine tudo, porque o enunciado pode pedir qualquer parte.

Parte 3 — Resolvendo, passo a passo

Passo 1 — Representação da solução

int vet_escolhido[MAX_ITENS];   // 1 = escolhido, 0 = fora. Sempre com exatamente k uns.
int fo;

O vetor binário responde "este item está dentro?" em O(1), e tem o tamanho de n.

Ponto de decisão: existe outra representação válida, um vetor de k índices (vet_indice[0..k-1]). Ela garante por construção que há k itens, mas exige cuidado para não repetir índice, e perguntar "o item i está dentro?" custa O(k). Usei o binário por ser mais simples. Se a prova der a struct, use a dela.

void calcular_fo(Solucao& s)

    for (int i = 0; i < num_itens; i++)
        if (s.vet_escolhido[i] == 1)
            s.fo += vet_valor[i];
}

Pontos de atenção: esquecer s.fo = 0 acumula a FO antiga a cada chamada. Se o enunciado dissesse "maximizar valor menos um custo", é aqui que o custo entra.

Passo 3 — O movimento (o passo mais importante deste exercício)

A ideia óbvia é "virar um bit", mas ela falha:

escolhidos = 4 (k = 4)
virar item 5 de 0 para 1  →  5 escolhidos   ✗ viola "exatamente k"
virar item 3 de 1 para 0  →  3 escolhidos   ✗ viola

Qualquer virada isolada quebra a restrição. O movimento que preserva a restrição é a troca: um item sai (1→0) e outro entra (0→1). Os dois mudam juntos e o total continua k. O movimento tem que levar uma solução viável a outra viável.

AlternativaO que muda
Virar 1 bit + penalizar na FO (− peso × |escolhidos − k|)vizinhança maior (n), mas passa por soluções inviáveis; o peso precisa ser grande o bastante para violar nunca compensar
Troca (a usada aqui)só soluções viáveis; vizinhança k(n−k)
Restrição "até k"virar 1 bit já serve (respeitando o teto)

Passo 4 — Tamanho da vizinhança

Escolhe-se quem sai (k opções) e quem entra (n−k opções): k × (n−k). No exemplo, 4 × 8 = 32 vizinhos. Esse número vira o parâmetro iteracoes da randômica.

Ponto de atenção: enumere "todos os pares (saindo, entrando)" e filtre com if/continue. Não tente adivinhar índices.

Passo 5 — gerar_vizinha e construtiva aleatória

// O movimento NÃO pode ser "virar um bit": isso deixaria k+1 ou k-1 itens (solução inviável).
// O movimento certo é TROCAR: tira um item escolhido e coloca um não escolhido.
void gerar_vizinha(Solucao& s)
{
    int saindo, entrando;
    do
        saindo = rand() % num_itens;
    while (s.vet_escolhido[saindo] == 0);             // precisa ser um item hoje escolhido
    do
        entrando = rand() % num_itens;
    while (s.vet_escolhido[entrando] == 1);           // precisa ser um item hoje fora
    s.vet_escolhido[saindo] = 0;
    s.vet_escolhido[entrando] = 1;
}

Pontos de atenção: se k = 0 ou k = n, um dos dois do/while nunca termina (não existe item escolhido, ou fora). Em instâncias normais não acontece, mas é isso que causaria um travamento. Os dois sorteios são independentes.

A construtiva aleatória sorteia itens e só conta quando o item estava livre:

// Escolhe k itens DIFERENTES ao acaso. Sortear "k vezes" poderia repetir o mesmo item e
// gerar menos de k escolhidos; por isso só conta quando o item sorteado ainda estava livre.
void heuristica_construtiva_aleatoria(Solucao& s)
{
    memset(s.vet_escolhido, 0, sizeof(s.vet_escolhido));
    int escolhidos = 0;
    while (escolhidos < num_escolhas)
    {
        int item = rand() % num_itens;
        if (s.vet_escolhido[item] == 0)
        {
            s.vet_escolhido[item] = 1;
            escolhidos++;
        }
    }
    calcular_fo(s);
}

void busca_local_melhor_melhora(Solucao& s)
{
    calcular_fo(s);
    while (1)
    {
        int melhor_saindo = -1;
        int melhor_entrando = -1;
        int melhor_fo = s.fo;
        for (int saindo = 0; saindo < num_itens; saindo++)
        {
            if (s.vet_escolhido[saindo] == 0)
                continue;
            for (int entrando = 0; entrando < num_itens; entrando++)
            {
                if (s.vet_escolhido[entrando] == 1)
                    continue;
                int fo_original = s.fo;
                s.vet_escolhido[saindo] = 0;
                s.vet_escolhido[entrando] = 1;
                calcular_fo(s);
                if (s.fo > melhor_fo)                 // compara com o melhor visto até agora
                {
                    melhor_fo = s.fo;
                    melhor_saindo = saindo;
                    melhor_entrando = entrando;
                }
                s.vet_escolhido[saindo] = 1;          // sempre desfaz
                s.vet_escolhido[entrando] = 0;
                s.fo = fo_original;
            }
        }
        if (melhor_saindo == -1)

        s.vet_escolhido[melhor_entrando] = 1;

    }
}

O que muda em relação ao PRCP e ao makespan:
  • Laços: em vez de ponto × posição, são saindo × entrando, com dois continue para filtrar os pares válidos.
  • Aplicar: dois bits mudam, não um.
  • Desfazer: os dois bits voltam, e a fo também. Esquecer um deles deixa a solução com k±1 itens, e o erro só aparece depois.
  • Melhor melhora: duas variáveis melhor_*, porque o movimento tem dois elementos.
  • Sinal: >, como no PRCP.

Parte 4 — Testar por um segundo caminho

Neste problema existe um caminho independente: o ótimo é a soma dos k maiores valores. Com os valores 15 3 22 8 19 5 30 11 2 27 9 14: 30 + 27 + 22 + 19 = 98. O programa calcula isso por fora e compara. Outras conferências: fo recalculada do zero = fo da solução; itens escolhidos = k (a restrição foi preservada pela busca inteira).

Resultado real (n = 12, k = 4, início aleatório)

MétodoFOItens escolhidos
inicial (aleatória)831, 3, 5, 10
randômica941, 3, 7, 10
primeira melhora983, 5, 7, 10
melhor melhora983, 5, 7, 10

Conferência final: FO 98 recalculada, 4 itens (= k). Ótimo conhecido: 98.

Parte 5 — Três coisas que este resultado ensina

  1. A randômica não garante ótimo local. Parou em 94, mas existia uma troca que dava 98 (tirar o item 1, de valor 15, e pôr o item 5, de valor 19). Dos 32 vizinhos, só 1 melhorava. A randômica sorteou 32 vezes e errou esse único vizinho; a chance disso é (31/32)32 ≈ 36%. A primeira e a melhor melhora varrem tudo e não têm esse problema.
  2. Pergunte se existe solução exata trivial. Aqui, pegar os k maiores já é ótimo, e uma gulosa resolveria sem busca local. Na prova isso raramente acontece, porque a FO não é uma soma simples. Mesmo assim, serve de prova de que o código está certo.
  3. A restrição ditou o movimento. Com bit-flip, a busca "melhoraria" escolhendo mais itens (mais itens, mais soma) e quebraria o "exatamente k" sem avisar.

Parte 6 — Onde o problema da prova pode ser diferente

Se o enunciado mudar para...O que muda no seu raciocínio
minimizar custo (menor soma)sinal vira <; o teste passa a ser a soma dos k menores

Versão enxuta (o que você escreveria no papel)

solução:    vet_escolhido[i] ∈ {0,1}, soma = k
FO:         soma dos valores com bit = 1            (MAXIMIZA, >)
movimento:  TROCA (1 sai, 1 entra); bit-flip quebraria o "exatamente k"
vizinhança: k × (n−k)
laços:      saindo (só os escolhidos) × entrando (só os de fora)
desfazer:   voltar OS DOIS bits + restaurar a fo
teste:      soma dos k maiores; fo recalculada; escolhidos == k

Teste-se (sem olhar o código)

1. Se o exercício pedisse minimizar o custo total de k itens, o que mudaria no código e no teste do ótimo?

Só o sinal da comparação (> vira <, nas três buscas) e, no melhor-melhora, o raciocínio de "melhor" (menor FO). O teste do ótimo passa a ser a soma dos k menores valores. A troca continua sendo o movimento, porque a restrição não mudou.

2. Na melhor melhora, por que são duas variáveis melhor_* e não uma?

Porque o movimento é identificado por dois elementos: quem sai e quem entra. Guardar só um deixaria impossível reaplicar a melhor troca no fim.

3. O que acontece se, ao desfazer, você restaurar só vet_escolhido[saindo] e esquecer o entrando?

O item entrando fica com 1 sem ninguém ter saído: a solução passa a ter k+1 itens. A FO recalculada soma um item a mais e a busca "melhora" de forma falsa, quebrando o "exatamente k" sem nenhum aviso. Por isso o teste final confere escolhidos == k.
