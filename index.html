Sobre a disciplina

Métodos de Otimização é a continuação natural de Otimização Linear, trocando o eixo de métodos exatos (Simplex, dualidade) por métodos aproximados: heurísticas construtivas, buscas locais e meta-heurísticas completas (Simulated Annealing, GRASP, Algoritmos Genéticos, entre outras).

Como as provas funcionam

Cada prova recebe um código-base parcialmente pronto e cobre uma técnica nova aplicada a um problema diferente — não é reescrever do zero, é completar métodos dentro de uma estrutura já dada. Existe também uma componente competitiva: bônus de nota para a melhor solução da turma.

Progressão de técnica
ProvaTécnicaFoco
P1ModelagemStruct de solução, leitura de instância, FO penalizada
P2Heurísticas construtivasAleatória, gulosa, aleatória-gulosa (RCL)
P3Busca localRandômica, primeira melhora, melhor melhora
FinalMeta-heurística completaSA, GRASP, AG com orçamento de tempo

Como interpretar a P1 (TSP) — questão a questão

Leitura do enunciado (prova1.pdf) cruzada com uma resolução real (gabriel_souza.h / gabriel_souza.cpp / instância toy.txt), linha do que o enunciado pede vs. o que precisa virar código, e os pontos onde é fácil perder nota por interpretar errado, não por não saber a técnica.

Erro que mais derruba nota nessa prova: a rota é um ciclo ("...retorne à cidade de origem"), não um caminho aberto. Se a FO não incluir a aresta de volta da última cidade para a primeira, todas as outras respostas ficam certas e a nota some assim mesmo.

Q1 · 0,5 Leitura da instância

O que o enunciado pede: "faça um método para leitura de uma instância... deve receber o nome/diretório do arquivo como parâmetro". E logo depois: "os dados necessários para o tratamento do problema devem ser armazenados em variáveis globais, que também devem ser criadas."

Como isso vira código: duas exigências separadas, fáceis de misturar. A função só recebe o caminho do arquivo (char* arq) e não retorna nada — quem guarda os dados são as globais num_cid e mat_custo_cid, criadas no .h fora de qualquer função:

// gabriel_souza.h int num_cid; float mat_custo_cid[MAX_CIDADES][MAX_CIDADES]; void ler_instancia(char* arq); // gabriel_souza.cpp void ler_instancia(char* arq) { FILE* f = fopen(arq, "r"); fscanf(f, "%d", &num_cid); for (int i = 1; i <= num_cid; i++) for (int j = 1; j <= num_cid; j++) fscanf(f, "%f", &mat_custo_cid[i][j]); fclose(f); }

Formato do arquivo (ver toy.txt): primeira linha é n, depois uma matriz n×n de custos, espaço-separada. toy.txt tem 5 cidades e é exatamente a instância que o enunciado manda usar "para depuração do código".

Pontos de atenção: a assinatura tem que bater literalmente com "recebe o nome do arquivo por parâmetro" — retornar uma struct de instância ou usar variável global para o nome do arquivo foge do pedido. E como os dados são globais, ler_instancia é chamada uma vez no main, antes de qualquer coisa que use num_cid/mat_custo_cid — nesse código, isso é reforçado indexando de 1 a num_cid (não de 0), então o vetor/matriz precisam ter tamanho MAX_CIDADES+1 de folga ou MAX_CIDADES já contar essa margem.
Q2 · 0,5 Struct de solução

O que o enunciado pede: "um tipo/estrutura de dados para armazenamento das informações referentes a uma solução... todas as informações necessárias devem fazer parte desse tipo." A palavra-chave é "todas" — não é só a rota.

Como isso vira código: uma solução do TSP precisa da sequência de visita e do valor da função objetivo já calculado para ela, porque a Q3 (escrita) e a Q4 (cálculo da FO) recebem essa mesma struct por referência e leem/escrevem em ambos os campos:

typedef struct TSolucao { int vet_seq_vis[MAX_CIDADES]; float fo; } Solucao;
Pontos de atenção: esquecer o campo fo na struct (deixando o valor "solto" numa variável separada) é o erro mais comum aqui — a Q4 pede explicitamente para calcular a função objetivo de uma solução, ou seja, o resultado tem que morar dentro da própria struct. MAX_CIDADES vem de um #define 200, batendo com a observação do enunciado ("código deve tratar instâncias com até 200 cidades") sem alocação dinâmica.
Q3 · 0,5 Escrita da solução

O que o enunciado pede: "escrever (tela e arquivo) de uma solução... deve escrever o valor da FO e a rota... a solução deve ser recebida por parâmetro (referência)." Duas saídas possíveis com uma função só, e passagem por referência é obrigatória (não por valor, não por ponteiro para struct nesse padrão).

void escrever_solucao(Solucao &sol, char* arq) { FILE* f = (strcmp(arq, "") == 0) ? stdout : fopen(arq, "w"); fprintf(f, "Valor da FO: %.1f\n\n", sol.fo); for (int i = 1; i <= num_cid + 1; i++) fprintf(f, "%d ", sol.vet_seq_vis[i]); if (strcmp(arq, "") != 0) fclose(f); }

A saída "tela e arquivo" nesse código é resolvida com um único parâmetro arq: string vazia "" escreve no stdout, qualquer outro valor abre um arquivo de verdade — uma função, os dois destinos do enunciado, sem duplicar lógica.

Pontos de atenção: o laço vai até num_cid + 1, não até num_cid — porque a rota impressa é o ciclo fechado (última posição repete a cidade inicial). Se a struct guarda só a FO e a sequência "aberta", a rota impressa fica sem o retorno à origem e não corresponde ao que a Q4 realmente calculou.
Q4 · 1,0 Função objetivo (com penalização)

O que o enunciado pede: "minimizar o custo total da rota... penalizando as cidades não visitadas e repetidas (pode-se usar o mesmo peso para os dois casos: α = 100)." E ainda: "para teste da Questão 4, pode-se criar 'à mão' uma solução" — ou seja, o enunciado já avisa que o main vai ter uma rota escrita manualmente para validar a FO, sem precisar de heurística nenhuma ainda.

Como isso vira código: a rota é um ciclo, então antes de calcular custo é preciso garantir que a última posição feche de volta na primeira cidade — esse código isola essa responsabilidade numa função separada, chamada antes de calcular_fo:

void verifica_ret_cid_ini(Solucao &sol) { if (sol.vet_seq_vis[1] != sol.vet_seq_vis[num_cid + 1]) sol.vet_seq_vis[num_cid + 1] = sol.vet_seq_vis[1]; } void calcular_fo(Solucao &sol) { int vet_count_vis[num_cid + 1]; sol.fo = 0; memset(&vet_count_vis, 0, sizeof(vet_count_vis)); for (int i = 1; i <= num_cid; i++) { int origem = sol.vet_seq_vis[i]; int destino = sol.vet_seq_vis[i + 1]; sol.fo += mat_custo_cid[origem][destino]; vet_count_vis[origem]++; } for (int i = 1; i <= num_cid; i++) { if (i == sol.vet_seq_vis[1] && vet_count_vis[sol.vet_seq_vis[1]] == 2) continue; // cidade inicial contando 2x = fechou o ciclo certo, não é erro if (vet_count_vis[i] == 0) sol.fo += ALFA; // nunca visitada if (vet_count_vis[i] > 1) sol.fo += ALFA; // visitada mais de uma vez } }
Conferindo com a instância toy (5 cidades):

No main, a rota de teste é 3 4 2 3 5 nas posições 1 a 5 — repare que a cidade 3 aparece duas vezes (posição 1 e posição 4) e as cidades 1 e 4 nunca aparecem. Isso é proposital: é o "à mão" que o enunciado libera para a Q4, servindo também para provar que a penalização funciona — uma rota assim deve custar mais caro que uma rota válida na mesma instância.

Pontos de atenção (onde a nota costuma cair):

1) sol.fo = 0 precisa vir no início da função — se calcular_fo for chamada mais de uma vez sobre a mesma Solucao sem zerar, o valor acumula do cálculo anterior.

2) A soma de custo do laço percorre i = 1..num_cid usando vet_seq_vis[i+1] como destino — só funciona porque verifica_ret_cid_ini já garantiu que vet_seq_vis[num_cid+1] existe e fecha o ciclo; pular essa chamada faz o laço ler posição não inicializada.

3) A exceção do continue existe porque a cidade inicial tem que aparecer 2 vezes no vetor contado (início e fim do ciclo) — sem essa exceção, toda solução válida seria penalizada por "repetir" a própria cidade inicial, o que é o comportamento oposto ao que o enunciado pede.
